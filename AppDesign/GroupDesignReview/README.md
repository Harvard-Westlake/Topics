# Group Design Review
*<font color="#8b949e">Review the three designs you back the most — with pull requests to prove it</font>*

<font color="#a371f7">Reinforce</font>

</div>

---

This is design review, round two — at scale. Instead of one partner, you will review **the 3 projects you have the highest financial influence toward**: the designs you bid on most heavily when the class allocated its investment. You back them; now make them better.

> **Note:**
> Your bids signal which designs you most want to succeed. Reviewing exactly those three keeps every review honest — you are improving something you have a stake in.

---

## <font color="#388bfd">Setup</font>

1. Make sure you are a **collaborator** on each of the three repositories:
   - Ask each owner to add you, and accept the invites
   - If an owner is absent, **fork their repository** instead
2. Add collaborators to **your own** project for anyone who wants to work on it

---

## <font color="#388bfd">Run the full review process — three times</font>

Follow all the design review documentation from the last review cycle in [Design Review](../DesignReview/):

- Work in a **new branch** for each review — never `main`
- Review the design's clarity, completeness, and implementation drift
- Check for Honor Code and law violations
- Add constructive ideas — glaze only if deserved
- Commit and open a **pull request**

Keep the language rules from [Design Communication](../Docs/design-communication.md) in force: the subject is the design, never the designer.

---

## <font color="#388bfd">Emphasize additional features</font>

Last design iteration, one of the review items included new ideas. Today, focus **additionally** on ideas that would make each project great **for users**:

- Add ideas for **user experience** — what would make using this smoother, clearer, more delightful?
- Add ideas for **overall application design** — behaviors and features that increase the product's value

This round is not just critique — it is contribution. Each of your three reviews should leave the design measurably richer than you found it.

---

## <font color="#388bfd">☑️ Check for Understanding</font>

### <font color="#79c0ff">Introductory</font>

- [ ] Explain which three projects you review today, and why those three.
- [ ] Name the fallback when a repository owner is absent.
- [ ] State how many pull requests you must have open by the end, and in how many branches.

### <font color="#79c0ff">Intermediate</font>

- [ ] Run the complete review process — branch, review, honor-code check, constructive ideas, PR — from memory.
- [ ] Write a user-experience feature addition that names the user benefit, not the mechanism.
- [ ] Explain the difference between this review round and the first Design Review lesson.

### <font color="#79c0ff">Advanced</font>

- [ ] Keep three parallel reviews distinct — each tailored to its design rather than copy-pasted feedback.
- [ ] Propose a feature addition that strengthens a design's *existing* identity instead of pulling it sideways.
- [ ] Argue why reviewing designs you invested in produces better feedback than reviewing at random.
