# Help a Classmate
*<font color="#8b949e">Fork a stranger's project, get it running from their README, and ship them a feature by pull request</font>*

<font color="#a371f7">Reinforce</font>

Your task is simple in theory but potentially harder in practice: **program something for another classmate**. You will do this twice — once each class period, for a different classmate's project each time.

This is the payoff of the documentation you all wrote in [Refactoring and the README](../RefactorAndReadme/). Their README is your only setup guide; their MVP.md is your only task list. If either one fails you, you are experiencing exactly what happens at a real company when documentation is bad — and your classmate is learning exactly where theirs fell short.

---

## <font color="#388bfd">The workflow</font>

1. **Fork their repo** — your own copy on GitHub that you can push to
2. **Clone your fork** — bring it down to your machine
3. **Follow their instructions in their README.md** to get their project up and running
4. **Solve one of the features in their MVP.md** — pick the highest-priority item, or something more sensible if their list is not prioritized correctly
5. **Update their MVP.md** — mark what you completed so the next contributor sees an accurate list
6. **Submit a pull request** back to their repository, clearly describing the purpose and the changes

The fork-and-PR mechanics are the same ones you learned in [Git Usage](../../GitUsage/) — this time on a codebase you have never seen, with stakes: your PR lands in someone's real project.

> **Tip:**
> Work in a feature-named branch on your fork and make at least three meaningful commits as you go. Your commit history is part of your grade — one giant "did everything" commit tells the reviewer nothing.

---

## <font color="#388bfd">How the 100 points split</font>

Each run of this assignment is worth **100 points**:

| Points | For |
|---|---|
| **50** | Getting their project up and running |
| **25** | Adding a feature that is working |
| **10** | Updating the MVP.md |
| **15** | Submitting a pull request |

> **Note:**
> Half the credit is just getting the project running from their README. That is not a freebie — following someone else's setup instructions on a machine they have never touched is the single most realistic test of documentation there is.

---

## <font color="#388bfd">What good work looks like</font>

The full grading rubric is on the [assignment page](ASSIGNMENT.md), but the shape of top-tier work is:

- **Git workflow** — proper fork, feature-named branch, a well-documented PR, and 3+ meaningful commits
- **Feature choice** — the top-priority item from their MVP.md, fully implemented and integrated
- **Understanding** — you can articulate what each commit does, why, and the trade-offs you chose
- **Code quality** — readable, consistent with their codebase, no stray junk files (no `.DS_Store` submissions)
- **Documentation** — their README/MVP.md reflect your addition, and your PR references the key commits

## <font color="#388bfd">Skill Building</font>

### <font color="#79c0ff">Introductory</font>

- [ ] Can you list the six steps of the workflow, from fork to pull request?
- [ ] Can you state the 100-point split and what each portion is for?
- [ ] Can you fork and clone a classmate's repository?

### <font color="#79c0ff">Intermediate</font>

- [ ] Can you get a project you have never seen running using only its README?
- [ ] Can you choose the right feature from someone else's MVP.md and justify the choice?
- [ ] Can you write a pull request description that explains the purpose and changes clearly?

### <font color="#79c0ff">Advanced</font>

- [ ] Can you implement a feature in an unfamiliar codebase while matching its existing style and structure?
- [ ] Can you update someone else's MVP.md so the next contributor sees an accurate, prioritized state?
- [ ] Can you explain the design decisions and trade-offs of your contribution in the PR, commit by commit?
